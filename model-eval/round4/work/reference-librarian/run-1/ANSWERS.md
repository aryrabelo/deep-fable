## Q1 — Gemini CLI skills outside an extension
**Verdict:** YES
**Confidence:** high
**Checked:** Gemini CLI official docs at geminicli.com (Agent Skills page, footer "Last updated: Apr 30, 2026"; Extensions page, footer "Last updated: Feb 17, 2026") and the `google-gemini/gemini-cli` repo (`main` branch, fetched 2026-08-19).
**Evidence:**
- https://geminicli.com/docs/cli/skills/ — official docs state Gemini CLI "discovers skills from several locations, following a specific order of precedence (lowest to highest): 1. Built-in skills ... 2. Extension skills ... 3. User skills: Located in `~/.gemini/skills/` or the `~/.agents/skills/` alias. 4. Workspace skills: Located in `.gemini/skills/` or the `.agents/skills/` alias." Extension-bundled skills are only one of four discovery tiers; user and workspace skill directories are read directly, with no extension manifest required.
- https://github.com/google-gemini/gemini-cli — the Gemini CLI project's own repo dogfoods this exact mechanism: it ships `.gemini/skills/<name>/SKILL.md` directories (e.g. `.gemini/skills/ci/SKILL.md`, `.gemini/skills/docs-writer/SKILL.md`) directly at the repo root, with no accompanying `gemini-extension.json` — a plain workspace skill directory, not an extension bundle.
- https://geminicli.com/docs/extensions/ — official docs describe extensions as a way to "package prompts, MCP servers, custom commands, themes, hooks, sub-agents, and agent skills" for distribution/sharing; this confirms extensions are an optional packaging/distribution mechanism, not the only way to load a skill.
**Impact on adapter:** The Codex/Claude-style adapter pattern (copy `SKILL.md` into a bare skill directory) works for Gemini CLI too — install to `.gemini/skills/j-space/` or `~/.agents/skills/j-space/` (workspace/user tier) with no `gemini-extension.json` needed; extension packaging stays a ROADMAP-only item for distribution, not a hard requirement.

## Q2 — Cursor per-project model override
**Verdict:** NO
**Confidence:** high
**Checked:** Cursor official docs at cursor.com (CLI Configuration reference and Rules reference), fetched 2026-08-19; reflects Cursor CLI config schema `version: 1`.
**Evidence:**
- https://cursor.com/docs/cli/reference/configuration — official docs give the exact file-location table: global `~/.cursor/cli-config.json` (or Windows equivalent) holds the `model` field (`"Selected model configuration"`), while project-level `<project>/.cursor/cli.json` exists, but the docs state explicitly: "Only permissions can be configured at the project level. All other CLI settings must be set globally." Model selection is exposed only via the global config file or the `/model` slash command, both user/session-scoped, not repo-committed.
- https://cursor.com/docs/rules.md — official docs describe the full `.cursor/rules/*.mdc` frontmatter schema (`description`, `globs`, `alwaysApply`) plus `AGENTS.md`/Team Rules/User Rules; none of the four rule types Cursor documents has any field or mechanism for selecting a model — rules only inject prompt-level instructions, they cannot pick a model.
**Impact on adapter:** The installer cannot ship a repo file that pins Cursor's model; it should only install the skill (to `.cursor/rules` or a skills-compatible path) and print that model selection is a user/global setting (`~/.cursor/cli-config.json` `model` field, or the editor's model picker) — never write to it.

## Q3 — Codex CLI legacy skills path
**Verdict:** YES
**Confidence:** high
**Checked:** `openai/codex` GitHub repo, `main` branch, file `codex-rs/ext/skills/src/host_roots.rs` (source code), cross-checked against the official Codex docs page at learn.chatgpt.com, both fetched 2026-08-19.
**Evidence:**
- https://raw.githubusercontent.com/openai/codex/main/codex-rs/ext/skills/src/host_roots.rs — the actual skill-root resolver (`roots_from_layer_stack`) contains, for the `User` config layer: `// Deprecated user skills location ($CODEX_HOME/skills), kept for backward compatibility.` followed by `roots.push(local_root(config_folder.join(SKILLS_DIR_NAME), SkillScope::User))`, pushed *before* the `~/.agents/skills` root (`home_dir.join(".agents").join("skills")`) that follows immediately after in the same match arm. `$CODEX_HOME` defaults to `~/.codex` (confirmed by the docs' own example path `~/.codex/config.toml`), so this is literally `~/.codex/skills`. `SkillCatalog::push_entry` (in `catalog.rs`) silently drops any later entry whose `(authority, id)` already exists, i.e. first-registered wins — so for a same-named skill present in both locations, the legacy `~/.codex/skills` copy (registered first) wins over `~/.agents/skills`.
- https://learn.chatgpt.com/docs/build-skills — the current official "Build skills" doc's location table lists only `.agents/skills` (repo, at three levels), `$HOME/.agents/skills` (user), `/etc/codex/skills` (admin), and system-bundled skills — it does not mention `~/.codex/skills` at all, confirming the legacy path is intentionally undocumented/deprecated even though the code still reads it.
**Impact on adapter:** Installing to `~/.agents/skills/j-space` remains correct and forward-compatible (it is the documented, primary location); no need to also write `~/.codex/skills/j-space` — but if a machine happens to already have an old skill of the same name under `~/.codex/skills`, note in the ROADMAP that it will shadow the new `.agents/skills` copy until removed, since the deprecated path is scanned first.

## Q4 — OpenCode config directory relocation
**Verdict:** YES
**Confidence:** high
**Checked:** `anomalyco/opencode` GitHub repo (formerly `sst/opencode`), `dev` branch, files `packages/core/src/global.ts` and `packages/opencode/src/skill/index.ts` (source code), cross-checked against official docs at opencode.ai, both fetched 2026-08-19.
**Evidence:**
- https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/core/src/global.ts — the `Global` module computes `config = path.join(xdgConfig!, "opencode")` using the `xdg-basedir` package's `xdgConfig` (which itself resolves from `process.env.XDG_CONFIG_HOME`, falling back to `~/.config`), and then in `make()`: `config: Flag.OPENCODE_CONFIG_DIR ?? Path.config` — i.e. the `OPENCODE_CONFIG_DIR` environment variable, when set, completely overrides the resolved config directory used everywhere `Global.Service`/`Global.Interface` is injected (including skill discovery via `Config.Service`).
- https://opencode.ai/docs/config/ — official docs, "Custom directory" section: "Specify a custom config directory using the `OPENCODE_CONFIG_DIR` environment variable. This directory will be searched for agents, commands, modes, and plugins just like the standard `.opencode` directory ... The custom directory is loaded after the global config and `.opencode` directories, so it can override their settings."
- https://opencode.ai/docs/skills/ — official docs list the fixed default skill locations (`.opencode/skills/<name>/SKILL.md`, `~/.config/opencode/skills/<name>/SKILL.md`, plus Claude/agents-compatible paths); the global one is exactly the `~/.config/opencode` tree computed from `Global.Path.config` in the source above, so relocating that base (via `XDG_CONFIG_HOME`) moves the global skills search path too.
**Impact on adapter:** For an OpenCode adapter, prefer `OPENCODE_CONFIG_DIR` (or `XDG_CONFIG_HOME`) as the documented, source-verified override point if the installer ever needs to target a non-default OpenCode config root; the default install target remains `~/.config/opencode/skills/j-space` (or the `.agents/skills` compatibility alias, which OpenCode also reads per `.opencode/skills/index.ts`).
